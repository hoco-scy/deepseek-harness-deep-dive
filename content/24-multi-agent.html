结论：这不是“群体智能调度器”，而是一组可组合的委派生命周期

DeepSeek Harness 的多 Agent 能力由四件事拼成：命名 SubagentProvider seam、一次性 SubagentRun、可冷恢复的 continuable child Session 及其进程内 Activation epoch，以及模型可见的委派/控制工具。这套 subagent subsystem 没有一个统一的 swarm、共享黑板、投票器或任务 DAG；协作来自父子 Session、inbox、持久 descriptor 和可选 provider 的组合。

这个结论很重要：看到 subagent 并不能推出子 Agent 是否继承历史、是否能继续对话、是否由 Job 管理，甚至不能推出它运行在同一进程。Provider 只承诺它明确声明的能力；不支持的 outputSchema、深度限制、工具过滤和 persona 会在启动前失败，而不是被静默忽略。

实际装配

Base bundle 注册 service、spawn/fork backend、控制与列表工具，并把 spawn 绑定为 continuable、fork 绑定为 one-shot；Web bundle 保留全局 registry/backend，却把模型可见工具移到每 Session preset。这里的“多 Agent”既是 runtime 能力，也是 composition 选择。

1. 真实拓扑：Provider 建子节点，Manager 管可继续会话

SubagentProvider.start() 拥有一次性 child 的发布前创建；返回 run 后，持有者负责等待结果并 dispose。对 continuable child，provider 只贡献“是否 seed 父历史”这份 detached data；身份、组合、Agent handle、消息、冷恢复、所有权和销毁全部由 continuation manager 接管。

术语边界：本仓库没有一个固定名为 delegate 或 spawn_agent 的通用 runtime 指令。委派工具名由配置决定；随附配置使用 subagent 与 subagent_fork，控制工具才是全局固定名。

因此“后台 Agent”不是一种状态：one-shot 后台是普通 Job，continuable 后台是有 durable Session ID 的对话。把两者都画成 running/done 会丢掉最重要的控制差异。

4. Spawn 与 Fork 的差异只在会话 seed，不在 child 是否“独立”

1

Spawn

不传 seed；child 从空对话开始，委派 prompt 必须自包含。

2

Fork

复制父 Session 从 seq 0 到最后一个 turn/end 的平衡前缀。

3

排除当前 Turn

正在调用委派工具的 Turn 尚未闭合，不能作为合法 child seed。

4

后续独立

两者都拥有新的 Session ID、自己的 inbox、Turn 和输出后缀。

上下文语义

Fork 的“继承上下文”仅指已完成对话历史；它不意味着共享当前 reasoning、live inbox 或同一个 Session。测试在父级第二个 Turn 悬挂时 fork，验证 child seed 只包含首个已完成 Turn。

两种 in-process child 都会加入父级正在运行的同一 preset generation——同一批 plugin instance、工具注册和 prompt section，而不是按 preset 名重新读取可能已变化的配置。

5. 继承矩阵：路线、工作区和能力是不同维度

项目规则是否耐久
Provider / model / maxTokens默认取父级，child request 可覆盖provider/model 写入 continuable descriptor；maxTokens 不写
Workspace / lineage继承 cwd，记录 direct parent、origin、depth，以及存在时的非零 seedLength写入 Session header
Prompt / tools加入父级 exact live preset，再叠 child persona/filterpreset ID 与 descriptor 支撑恢复
Conversation只有 fork 复制 completed-turn prefixseed 成为 child 自己的 log 前缀
Sandbox / approvalSandbox policy 已组合时只复制显式 Session override；approval 已组合时钉为 never只有已定义的 override 才成为 delegation-source event

不会继承的内容同样重要：spawn 不看父 transcript；fork 不看 open Turn；一次性授权不会下放；部署 sandbox 默认值不会被快照；child 的 persona 和工具过滤只在自身 scope 中生效，不污染父级或 sibling。

设计判断

这里的继承不是对象浅拷贝，而是有意拆开的四条通道：Session seed、Agent options、preset scope 和 durable policy events。这比一个含糊的 inheritContext=true 更可审计。

6. 递归预算和权限边界都沿父子 lineage 单调收紧

Tool loader 的默认 maxDepth 是 3；provider-managed 用于无法由父 runtime 强制的外部 provider。底层 depth 读取持久 header 与 runtime option 的较大值，再加一生成 child，因此恢复后的 child 不能伪装回 depth 0。Direct apply 若省略 cap 则可无上限，这说明“默认 3”属于工具配置，不是 service 的全局定律。

调用权限

send_message 只允许 exact live direct parent；interrupt_agent 可以由 exact live ancestor 作用于更深 descendant。身份比较的是活 Agent 对象与持久 parent lineage，不是调用者提交一个可猜的 Session 字符串。

这不是 role-based team：没有 leader/member 角色表，也没有 sibling 直发通道。现有 authority 是树形且窄化的；想做 team、共享队列或任意 Agent 路由，需要新增显式协议，而不是把现有 parentSession 当成万能 ACL。

7. One-shot 的核心合同：发布前 provider 所有，发布后 run holder 所有

validate provider + capabilities + schema + descriptor
  → provider.start()
      → unpublished setup / rollback on failure
      → publish child or external run
  → emit subagent/start
  → await run.result ──────────→ emit subagent/end
  → map stopReason / preserve partial output
  → holder runs dispose() to quiescence
提交点

Provider 启动 reject 时没有 run、也没有 lifecycle edge；一旦返回，Turn/transport failure 进入 result。In-process driver 发布 child 后只提交一个 user prompt并等待 idle，AbortSignal 会 cancel child；dispose() 是幂等资源释放边界。

结果从 seed/activation boundary 后的 child-owned suffix 读取。completed、aborted、error、max-tokens、refusal 不会被压成一个布尔值；取消或截断仍可携带 partial output。One-shot 的 subagent/end 跟随 result settlement，可能早于 holder 完成 dispose；continuable epoch 的 end 则等待 teardown outcome。后台 Job 只有 completed 才把 final text 当成功输出，其他 reason 映射为 killed/failed，并且总在 settle 后 dispose。

8. “最终答案”与“结构化结果”是两套独立提交协议

普通输出的统一选择规则是最后一条非空 assistant message；若没有，则使用累计 text delta；都没有才为空。选择与 stop reason 独立，因此 error/max-tokens 也可能携带诊断价值很高的 partial answer。

Structured output

只有支持该 capability 的 in-process provider 才会在 child scope 安装真实 schema 的 structured_output 工具、专属 prompt 和单调 guard。模型调用工具只是 staged；必须等 authoritative tools/result 成功，Code Mode 下还要等外层调用成功，才提交 capture。Child 声称 completed 却没有有效 capture 时，run 被改判为 error。

这解释了 external provider 为什么声明零 capabilities：工作目录相同不代表父 runtime 能强制其工具 catalog、persona、递归预算或结构化提交点。

9. Continuable 的 durable Session 与 process-local Activation 必须分开看

状态依据含义
runningAgent 正运行，或有已接受但尚未离开 inbox 的 waking message当前 epoch 不能 settle
waitingAgent idle，但仍拥有未 dispose 的 child Activation父级被子树所有权钉住
settledAgent idle 且 owned children 为空dispose live handle；durable Session 仍可再恢复

Activation 是一个驻留 epoch，不是 durable Task。它持有 exact handle、弱引用 ancestry、owned-child set、accepted message IDs 和一次性 disposal transaction；稳定的是 child Session ID，每次冷恢复会获得新的 lifecycle runId。

边界：只有 continuation-managed parent 会因 child 存活而进入 waiting。顶层 parent 不在这张 ownership graph 中；它是否继续工作由自己的 Turn/inbox 调度决定。

10. Follow-up 的权威提交点是 inbox acceptance；冷恢复不再调用 provider

send_message(childId)
  ├─ resident + running → 排入同一 Agent inbox，等当前 Turn 结束
  ├─ resident + waiting → 唤醒同一 Agent
  └─ no Activation      → inspect durable Session
                           → 校验 exact direct parent
                           → fold own descriptor suffix
                           → ctx.agents.resume()
                           → 排入 inbox

每个 child 的 delivery、release 和 disposal 先经过同一把 ChildLock；Agent inbox 是唯一 FIFO。调用方 AbortSignal 只拥有 acceptance 之前的阶段，消息被接受后不能通过这次 send_message 取消。

Provider 不参与恢复

Cold resume 从持久 Session header 和 child 自己 suffix 中的 descriptor 重建 provider/model、persona 与 tool filter，然后直接走 agents.resume()；它不 dispatch 原 provider。因此 provider 卸载会阻止新 start，却不必阻止已有 continuable child 恢复。Descriptor 不保存 maxTokens 或 outputSchema，恢复时不能假定这两个 activation-local 约束仍然存在。

11. 返回通道有四种，完成与报告绝不能混为一谈

通道谁发送会不会结束 childParent 得到什么
Foreground resultrun holder是，一次性直接 tool result
Background Job outcomeJob runtime是，一次性Job 状态/通知
reportContinuable child 主动选择否direct parent inbox 的 relay
Settlement noticeContinuation manager在 teardown 后发送stop reason + 可用 closing message

send_message 只返回被接受的 messageId，不是 child 的回答。Child-scoped report 只能发给 direct parent，可按 wakeup 或 quiet 调度，且报告不会结束 Turn/Activation。

兜底通知

只要 caller 曾收到 child ID，Activation settlement 就独立于 report 尝试投递 runtime notice；即使 max-tokens、失败、取消或 child 忘记报告，parent 仍有机会看到结果。Parent 已不 live 时通知被丢弃而不阻塞 teardown，child Session 是剩余的 durable record。

12. list_agents 是发现面，不是任务结果面

底层 listing 从 live Session store 与可选 persistence 合并 corpus，按 durable header 的 origin:subagent 找 direct children/descendants，再通过 projection 分类 mode/label。冷读并发固定为 4；单个 child 损坏或暂时读不到会成为 corrupt/unavailable diagnostic，而不是让整次 listing 失败。它不读取 Activation manager 或 provider 状态。

模型状态真实含义不是
runningLive Agent 正在驱动某个 Job 的 running
idleLive Agent 在 Turn 间；可能正等 descendant已完成、可收集结果
ready只有存储记录，可被 direct parent 恢复terminal success

模型工具过滤掉 one-shot child，因为它们不能被 send_message；descendants 仍会穿过这些节点做稳定 pre-order 遍历。Depth 1 才能 follow-up，更深节点只可作为 ancestor interrupt 候选。

13. 并发策略是“跨 child 可重叠、单 child 线性化”，不是全局调度

可并行部分

Provider contract 明确允许不同 child 的 starts 重叠；委派工具声明 concurrency-safe，并在 continuable prompt 中鼓励把独立委派放进同一 assistant message。One-shot background 还会进入 Job registry 的 owner capacity 规则。

必须串行部分

同一 durable child 的 follow-up、释放和销毁由 ChildLock 排队；accepted-ID set 覆盖“消息已同步插入、Agent status 尚未切到 running”的微任务窗口，避免 settlement 提前赢过已经接受的工作。父级 owned-child set 又把整个 descendant 生命周期纳入 parent settle 条件。

Subagent 层没有全局 worker pool、公平队列、优先级、配额分配或结果归并器。它提供正确的并发边界；“派几个、何时派、如何合并”仍由模型 prompt、Job 层或更高阶 workflow 负责。

14. Interrupt 只停当前 Turn；Drain 才销毁整棵 Activation 子树

操作立即动作保留内容完成等待
Foreground AbortSignalcancel one-shot child/run已产生 partial outputholder 最终 dispose
Job killabort task-owned controllerJob identity 到 settlementJob producer settle + dispose
interrupt_agentcancel(..., keepInbox:true)Activation、未 claim 消息、descendants不等待，fire-and-return
Manager/scoped drain同步关闭 admission，自顶向下 cancel只保留 durable Session自底向上 release，汇总失败

Interrupt 对 absent/已完成/one-shot ID 是 accepted no-op；它不是 subtree kill。外部 one-shot provider 在本地取消赢得竞态时把结果归一化为 aborted，并由幂等 handle teardown 等到子进程树退出。

树级静止

Drain 先封 admission，等已接纳 materialization 发布或回滚，再对所有 root 并行；每棵树先 top-down 传播 cancel、后 child-first 释放 handle。单支失败不会跳过 sibling，最终以 aggregate error 报告。最终 Session flush 是 best effort；失败会警告“恢复可能缺失或陈旧”，但不能永久钉住 ancestor。

15. 耐久性来自 Session descriptor，不来自驻留 Agent 或 Task queue

Session header
  parentSession / origin=subagent / delegationDepth / seedLength / agentPreset

subagent/descriptor v2（model-hidden, log-only）
  one-shot:    mode / provider / optional label
  continuable: mode / provider / label / agentProvider / agentModel / persona / toolFilter
  intentionally omitted: outputSchema / maxTokens / subagentDepth

Continuable creation 把 fork prefix（若有）之后追加一个 between-turn descriptor seed，再接受初始 prompt。Descriptor 先做 lossless JSON snapshot；当前版 parser 拒绝未知字段，版本不支持则不可恢复。

Ancestor descriptor 防串台

Fork seed 可能含祖先的 descriptor。Cold resume 因此只 fold seedLength 后的 child-owned suffix；projection 则采用 last valid descriptor wins，让 child 自己的记录覆盖 seed 中祖先身份。两处规则目的相同，折叠边界不同。

进程重启后可恢复的是 child 对话及其声明式 composition，不是旧 Activation、run handle、accepted set 或 background Job。最终 flush 失败时，runtime 仍释放 graph，明确选择“可能 stale 的恢复”而不是“确定死锁的祖先”。

16. Codex 对比：DeepSeek seam 看到一个 one-shot worker，Codex 内部仍可能编排 subagent

仓库里的 codex provider 每次委派启动新的官方 codex app-server --stdio，只继承父 Session 的 cwd。它声明零 start capabilities、没有 prepareContinuable、不共享父 transcript/preset/tool scope，也不返回本地 Agent handle。换言之，DeepSeek Harness 只把整个 Codex 运行包装成一个 one-shot child；即使该 Codex Turn 内部使用自己的 subagents，那棵内部树也不会成为 DeepSeek continuation graph 的可寻址节点。

1

启动

固定命令，初始化 JSON-RPC；thread 创建成功前不发布 run。

2

隔离

thread/start 强制 ephemeral:true，cwd 指向父工作区。

3

执行

仅接受非空 text blocks，启动一个 Turn。

4

回收

关闭 wire、结束 stdin、终止并等待整个受管进程树。

Wire 只把最后一个 final_answer（无显式 final 时退回最后个 unphased answer）作为输出；commentary 与 reasoning 不返回。Context window exceeded 映射为 max-tokens，其他异常经 shared out-of-process settlement 变成 error/partial output。

无人值守安全

Command/file approval 只会选择 cancel 或 decline，permission 请求返回空权限，user input 返回空 answers，MCP elicitation 被拒绝；没有把 child 的审批请求冒充成人类已同意。对应协议测试还验证 ephemeral thread、跨 thread/turn 过滤、commentary 排除和 last-final 选择。

比较结论

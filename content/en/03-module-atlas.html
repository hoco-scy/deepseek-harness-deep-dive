Correcting the first scale illusion

The root architecture diagram shows only dozens of central services, but the pinned packages/ tree contains 49 groups and 219 npm workspace packages. They are not 219 peer “business modules.” Some declare services, some implement providers, some expose capabilities only as model tools, and many are host/client/UI surfaces, composition bundles, test support, or zero-dependency utilities.

Source fact

The official package map requires extension plugins to depend on Service Definitions instead of concrete providers. A capability splits into packages when definitions, providers, and consumers need to evolve independently, and UI, hooks, and tools depend on the abstract agent service rather than a concrete loop.

Mechanism-level deduction

DeepSeek Harness cannot be understood by reading directories in isolation. The more effective unit is a capability closure: definition → one or more providers → model/host consumer → bundle assembly → session-event/UI projection → invariant and real-composition tests.

Six research planes

Product spine

core, llm, session, context, and compaction define how one Agent step actually happens.

Execution world

subprocess, shell, terminal, fs, sandbox, code-runtime, lsp, web, and e2b ground tools in local or remote execution environments.

Collaboration and orchestration

interaction, plan, goal, todo, jobs, subagent, workflow, skill, and mcp manage human-Agent and Agent-Agent coordination state.

Composition and data

boot, bundle, preset, settings, credentials, storage, workspace, and attachment determine runtime trees and ownership of non-session data.

Product surfaces

api, typert, sdk, acp, host, and client expose one runtime to the Web, stdio JSON-RPC, and automation protocols.

Proof and support

runtime-diagnostics, test-support, guard, session-query, feedback, util, and examples supply invariants, test assemblies, diagnostics, and low-level primitives.

Classification note: these six planes are cross-sections introduced by this report, not an official upstream hierarchy. One package group may span several planes.

Why every package has an invariant

Repository policy

Every package must own ./invariant: packages with runtime relationships register checkable event/data relations, while pure installation packages state a package-specific reason for an empty check. Registry contributions also require disposal tests proving that a contribution disappears when its fiber unmounts.

Design assessment

This directly addresses a common weakness of plugin architecture. Type checking proves local package interfaces, not that the final composition mounted exactly one provider, consumer, and coherent event relationship. Per-package invariants move part of “still correct after composition” into the runtime. The cost is additional installer and relationship-assertion maintenance across 219 packages.

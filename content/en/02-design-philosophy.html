One-sentence conclusion

The central philosophy of DeepSeek Harness is not to give the Agent more built-in powers, but to decompose the product into a network of capabilities that are composition-configurable, scope-isolated, reversibly mounted, and event-traceable. Complex features should remain plugins outside the loop and participate through stable service and event seams.

That sentence mixes facts with synthesis. This chapter separates them.

Principle 1: no privileged core, but an architectural constitution

Source fact

A Cordis context accepts services, typed events, and reversible effects. Model adapters, tool registries, session logs, and even the agent loop are assembled as plugins; extensions mount peer plugins instead of patching a privileged core.

Mechanism-level deduction

“No privileged core” does not mean “no core.” What cannot be casually replaced is the composition protocol: context scopes, event order, effect disposal, waterfall delegation, session-event compatibility, and the definition/provider/consumer relationship. Replacement implementations must still obey this protocol.

Design assessment

The benefit is that features need not continuously inject branches into one giant loop, and profiles or per-Agent presets can compose plugins. The cost is that correctness moves from local class logic into the global properties of a plugin graph, event ordering, and configuration layers.

Principle 2: registration is a reversible lifecycle effect

Repository policy

Contributions must register through ctx.effect() or ctx.on(), registry register() calls return disposers, and a waterfall listener must explicitly call next() to yield control downstream.

Mechanism-level deduction

A plugin's presence is not a permanent process fact; it is a lease bound to a Cordis scope. Disposing that scope must retract services, tools, listeners, and providers. This enables per-session and per-Agent composition plus runtime self-modification, while making every side-channel registration an architectural violation.

Principle 3: composition over hidden defaults

Source fact

A running dsh tree begins as an empty entry list and applies bundles, the profile patch, the home-level patch, and command-line overlays in order. Patches address rows by ID and replace the row's entire config or insert a new row.

Repository policy

Cross-package defaults must be resolved explicitly by the implementation that owns the semantics. Deployment tunables become validated configuration, and invalid configuration should fail at the earliest decidable point.

Design assessment

Explicit layers make the effective runtime tree printable, overridable, and auditable. Yet wholesale config replacement is not deep merge: an upper patch must understand the complete lower configuration shape or risk dropping fields while changing only one value. Predictability is purchased with author discipline.

Principle 4: what the model sees must become a durable fact

Source fact

The session log is the source of truth for model history, and deriveMessages() projects model messages from events. Raw assistant/chunk events remain available for replay and UI fidelity. Any newly model-visible input requires a session event and is checked by runtime invariants.

Mechanism-level deduction

This rule turns prompt engineering into event modeling. A plugin cannot secretly concatenate a string immediately before dispatch; if content affects model behavior, the log must reconstruct it. Resume, fork, telemetry, snapshots, and UI state no longer need independent stories for “what the model saw.”

Design assessment

This is one of the most valuable and expensive constraints in the design. It greatly improves audit and replay, but every dynamic context source needs event semantics, compatible readers, and derivation rules instead of one-off middleware state.

Principle 5: a capability is a closed three-role seam, not merely an interface

Source fact

The repository describes a replaceable capability through three roles: a Service Definition declares the contract, a Service Provider implements it, and a Consumer uses it—often through a model-visible tool. A single role does not form a complete seam.

This prevents the presence of an interface from being mistaken for replaceable architecture. Filesystem capability requires not only ctx.fs, but also local/sandbox/E2B providers, model-facing consumers, observation policy, an error vocabulary, and consistency with the process execution world.

Principle 6: simplify inside trusted static boundaries; validate real trust boundaries

Repository policy

Same-process values already constrained by static types are not repeatedly subjected to hostile runtime checks. Parsed configuration, queued data, model/tool JSON, persisted files, workers, processes, and wire protocols must be validated. Cross-boundary IDs use branded types rather than plain strings.

Design assessment

The principle is not “more validation is always safer,” but “spend validation effort where a value may be forged, drifted, or distorted.” Internal code stays readable; the risk is that misclassifying external data as a trusted typed value removes a defense entirely.
